## Binding constraints
- The handler imports no other first-party package (`curation`, `api`, `chat`, `shared`, `contracts`). The request rules stay in the agent; the Lambda only checks JSON shape and a byte cap (source: intent Constraints, architecture principles).
- The agent's reply is forwarded as `{"answer", "sources"}` only. The Lambda never adds, renames or filters fields beyond selecting those two keys (source: AC1, CA-1).
- API Gateway owns CORS: the handler emits no CORS headers (source: `src/api/handler.py` precedent).
- Account `626259825216`, region `us-east-1` and the runtime id `ai_radar_chat-JFCO0R9lkT` are pinned literals in the construct, with their tests (source: `CLAUDE.md` account migration note).
- `AiRadarChatApi` must deploy with `-c chat_api_reserved_concurrency=none` while the account Lambda quota is 10 (source: README account migration, FA-R1).
- Lambda timeout and the invoke read timeout are both shorter than API Gateway's ~30 s integration limit (source: intent Constraints).
- The Lambda role grants `bedrock-agentcore:InvokeAgentRuntime` on the chat runtime ARNs and log writes on its own log group, with no `*` resource and no managed policy (source: AC6).
- API Gateway access logging stays off, so no caller IP is recorded (source: AC7).
- No existing file under `chat_app.py`, `src/chat/`, `src/shared/`, `src/api/`, `infra/lib/{feed_api,chat_runtime,agent_runtime}.py` is modified (source: AC8).
- The Python package manager is `uv` only. The image installs with `uv export --only-group chat_api` (source: `CLAUDE.md`, AD-1 pattern).

## Proposed approach
Revisable by the executor if it records why.
- Decision: one Lambda, one route, `POST /v1/chat`, copying `feed-api`'s structure (HttpApi, `HttpLambdaIntegration`, stage throttle through the `CfnStage` escape hatch) — rationale: proven, reviewed pattern in this repo; rejected: adding the route to `AiRadarFeedApi` (breaks FA-4 and AC8; discussed with the human, separate API confirmed).
- Decision: the handler calls `boto3.client("bedrock-agentcore").invoke_agent_runtime` with `agentRuntimeArn` from an environment variable set by CDK, `runtimeSessionId` a fresh `uuid4` string (36 characters, above the service minimum of 33), `qualifier="DEFAULT"` set explicitly, `contentType`/`accept` `application/json`, and `payload` the validated request body bytes. The reply is `response["response"]`, a streaming body read to completion and parsed as JSON. — rationale: matches the operation model verified locally (`runtimeSessionId` min 33, `payload` blob, `response` stream); rejected: reusing one session id (couples unrelated callers to one runtime session).
- Decision: the client is built once per container with botocore `Config(connect_timeout=3, read_timeout=22, retries={"total_max_attempts": 1})`; the Lambda timeout is 28 s. A botocore read-timeout maps to 504 `upstream_timeout`; every other invoke exception maps to 502 `upstream_failure`. — rationale: a retry would double the Sonnet spend on a slow turn, and 28 s sits under API Gateway's limit; 3 s connect plus 22 s read leaves 3 s of headroom for the response and the log write. Revision 2 correction: Revision 1 specified `retries={"max_attempts": 1}`, but in botocore `max_attempts` counts retries beyond the first call, so it allowed two calls and a retried read timeout outlasted the Lambda timeout (audit round 1, F1, proved with a socket probe); `total_max_attempts` counts the first call, so `1` means no retry. Rejected: default retries, and `max_attempts`.
- Decision: the response mapping is: agent `{"error":"invalid_request", ...}` -> 400 with the agent's body; agent `{"error":"upstream_failure"}` -> 502; a body with `answer` (str) and `sources` (list) -> 200 with only those two keys; anything else (not JSON, unknown shape, unknown error) -> 502 `upstream_failure`. — rationale: the Lambda trusts nothing it does not recognise; rejected: passing unknown agent output through.
- Decision: local pre-checks are body present, valid JSON, a JSON object, and a UTF-8 byte length of at most 524,288 (512 KiB; the agent's own maximum is about 81,000 characters, so even 4-byte characters stay under it). A failure returns 400 `invalid_request` with `detail` one of `body_missing`, `body_not_json`, `body_not_object`, `body_too_large`, without invoking the agent. `history` is not defaulted by the Lambda: the agent already treats it as optional per CA-3, and the payload is forwarded as sent. — rationale: the agent stays the single owner of the rules (CA-3); rejected: duplicating the caps in the Lambda.
- Decision: one `chat_api_request` record per request through `json.dumps`, with `status`, `outcome` (`ok`, `invalid_request`, `upstream_failure`, `upstream_timeout`), `question_chars`, `history_items` (best-effort, zero when unparseable), `duration_ms` and the `session_id` it generated. It never holds the body, the answer or the caller's address. Handler exceptions are logged and answered 502 for the upstream call path, or 500 `internal_error` for a bug before it. Revision 2 clarification (human-approved 2026-10-20): the 500 path logs the exception CLASS NAME plus the stack frames (file, line, function) and never the exception message, because an unexpected exception in our own code could echo part of the request body; the rendered record, traceback included, therefore contains no exception text. Upstream AWS errors keep the full `exc_info` under `chat_api_upstream_error`, since AWS messages carry no user text. — rationale: lets a failed call be tied to a runtime session without recording text.
- Decision: stage throttle `throttling_rate_limit=5`, `throttling_burst_limit=10` as module constants in `infra/lib/chat_api.py`; CORS `POST` and `content-type`, origins default `["http://localhost:3000"]`, never `*`; both overridable by CDK context (`chat_api_allowed_origins`, `chat_api_reserved_concurrency`, with `none` meaning omit the kwarg). — rationale: same one-line-flip override pattern as the feed API.
- Decision: settings (`CHAT_RUNTIME_ARN`) load through `pydantic-settings` in `src/chat_api/config.py`, so a missing ARN fails at import with a typed error. — rationale: repo convention (config-loading capability); the group therefore holds `boto3` and `pydantic-settings`.
- Decision: the image bundles the locked `boto3` (not the base image's) through `--only-group chat_api`. The group's lower bound is set so that `boto3.client("bedrock-agentcore")` exists; the Dockerfile test and the real image build both check it. — rationale: the Lambda base image's boto3 may predate the client.
- Decision (Revision 2): the handler module sets its own logger to `INFO` (`logging.getLogger(__name__).setLevel(logging.INFO)`), so the `chat_api_request` record is emitted whatever the Lambda runtime's root level is. — rationale: the Python Lambda runtime leaves the root logger at WARNING unless a log level is configured, so an `INFO` record is likely dropped in CloudWatch (audit round 1, F2); a handler-level setting is testable offline and needs no infra or log-format change; rejected: `ApplicationLogLevel` with JSON log format, which changes the log wrapper and needs a deploy to take effect.
- Decision (Revision 2): the 28 s Lambda timeout, 22 s read timeout and 3 s connect timeout are module constants checked together by one test, so headroom cannot silently disappear (audit round 1, F6).
- Decision: add `src/chat_api/AGENTS.md` (purpose, key files, commands), since `harny-doctor` warns on a component without one.

## Risks
| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| A fresh session id per request forces an AgentCore runtime cold start each time, pushing latency toward the 28 s budget and adding cost | Med | High | AC9 records cold and warm latency live; if p50 is high, amend the spec to bucketed session ids (the agent is stateless, so sharing is functionally safe) |
| Lambda base-image boto3 lacks the `bedrock-agentcore` client | Med | High | Bundle boto3 via the group; the Dockerfile test and a real image build/import check catch it (the `feed-api` gotcha in `CLAUDE.md`) |
| IAM resource for `InvokeAgentRuntime` is too narrow (runtime vs endpoint ARN) | Low | Med | Docs show the action needs both the runtime ARN and `<arn>/runtime-endpoint/DEFAULT`; grant exactly those two, no wildcard. AC9 proves it live, and an `AccessDenied` is fixed in the construct and its test |
| Retry semantics are misread again (`max_attempts` vs `total_max_attempts`), doubling spend | Low | High | A test asserts `total_max_attempts == 1` on the built client's config, and the AC9 runbook reads the agent-side invocation count for one slow request |
| The `chat_api_request` record is dropped by the runtime's default log level | Med | High | The handler sets its own logger level; a test emits with the root logger at WARNING and asserts the record still reaches a handler; AC9 reads the record in CloudWatch |
| A rate-limited or abusive caller drains the Sonnet budget | Low | High | 5 rps / burst 10 stage throttle, the existing `AiRadarBudget` alerts, and the AC9 throttle check |
| Reserved-concurrency override forgotten on deploy | Med | Low | The stack default stays the audited value; the runbook shows the `none` flag, as for feed-api |
| Docker is not available to the executor for the image build check | Med | Med | That check is a documented human step in AC9; unit and synth tests do not need a daemon |
