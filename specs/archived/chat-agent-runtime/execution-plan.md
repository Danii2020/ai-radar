## Binding constraints
- `src/chat/` imports only `shared` and its own modules; `curation`, `shared` and `api` never import `chat`; `bedrock_agentcore` is imported only by files at the repo root (source: architecture-principles boundary 1, `runtime-deployment` invariant 1, CR-9).
- The graph and request modules contain no AWS client construction: the retriever and the model call are injected or reached through the existing `shared` seams, so the graph stays portable (source: CLAUDE.md "LangGraph-portable logic separate from infra").
- The chat role is separate from the curation role and grants `dynamodb:Query` on the `feed-by-score` index ARN only, with no table-level or write grant (source: intent AC7; feed-api AD-6 precedent).
- Config through `pydantic-settings`, explicit `validation_alias`, typed and fail-fast at import (source: config-loading).
- The AgentCore starter toolkit builds the `Dockerfile` found at the agent's `source_path` (the repo root) and ignores any other Dockerfile name (source: `container.py` `generate_dockerfile`, which copies `<source_path>/Dockerfile`). A second agent therefore cannot have a second Dockerfile in the same source tree.
- The `agentcore destroy` gotcha stands: null `aws.execution_role` in `.bedrock_agentcore.yaml` before `agentcore destroy`, or the CDK-owned role is deleted (source: README `runtime-packaging` runbook).
- Titan stays `dimensions=EMBED_DIM`, `normalize=True`; the Sonnet request shape (system prompt with `cachePoint`, `temperature`) is unchanged from Phase 0 (source: `shared/chat.py`).
- Deploy steps run only with the human's explicit go-ahead, one at a time. No role runs them unprompted (source: intent Constraints).
- `.bedrock_agentcore.yaml` is gitignored local toolkit state and is never committed (source: `.gitignore`).

## Proposed approach
Revisable by the executor if it records why.
- **Decision:** one stateless entrypoint, `chat_app.py`, a plain `def handler(payload)` decorated with `@app.entrypoint` — rationale: the SDK runs sync handlers in a thread pool, so blocking boto3 calls never stall `/ping`, and no background task or single-flight guard is needed because a turn is request/response; rejected: `async def` with `asyncio.to_thread` (extra machinery for no benefit) and the curation agent's ack-then-background pattern (chat must return the answer).
- **Decision:** request handling order in the handler: `parse_request` (pure, in `chat/request.py`) -> run the compiled graph -> build `{answer, sources}`. A parse failure returns `{"error": "invalid_request", "detail": ...}` before the graph is invoked, so no client is touched (AC3). Any exception from the graph is logged with `logger.exception` and returned as `{"error": "upstream_failure"}` (AC5).
- **Decision:** validation rules, pinned here because `Converse` requires them: `question` is a non-empty string of at most 1,000 characters after stripping; `history` defaults to `[]` when absent, must be a list of at most **20 items** (10 turns, one turn being a user item plus its assistant reply), each `{"role": "user"|"assistant", "text": str}` with `text` non-empty and at most 4,000 characters, and the roles must alternate starting with `user` and ending with `assistant`. The three limits are settings (`CHAT_MAX_QUESTION_CHARS`, `CHAT_MAX_HISTORY_TURNS`, `CHAT_MAX_HISTORY_ITEM_CHARS`) in `chat/config.py`. The `detail` is a short rule name (for example `question_too_long`), never an echo of the input.
- **Decision:** `chat/graph.py` builds a two-node `StateGraph`: `retrieve` (calls `retriever.search(question, k)`, records `retrieval_ms`) then `answer` (calls the shared answer function, records `model_ms`). State carries `question`, `history` (already in Converse message form), `hits`, `answer` and the two timings. `build_chat_graph(retriever, k)` takes the retriever as a parameter so tests inject a fake. The compiled graph and `DynamoCardRetriever` are built once per process at import of `chat_app.py`; no per-conversation state is held.
- **Decision:** when `retrieve` returns no hits, the `answer` node returns a fixed "the collected news does not contain this" message with `sources: []` and makes **no model call** (AC4) — rationale: deterministic, cheaper, and impossible to hallucinate a citation; rejected: calling Sonnet with an empty context block (non-deterministic, and the Phase 0 prompt does not define that case).
- **Decision:** `sources` are built from the hits in rank order: `{"n": i, "title", "url", "source", "published", "score"}` with `score` rounded to 4 places and `published` possibly `null`. The `[n]` in the answer is the position in this list, exactly as `_context_block` numbers the cards. No other card field and never a vector (AC1).
- **Decision:** the answer function in `shared/chat.py` takes prior messages in Converse form. The entrypoint converts client history items `{"role", "text"}` to `{"role", "content": [{"text": ...}]}`. `RagChat.ask` keeps its own `self.history` and calls the same function, so `run_chat.py` and the agent share one prompt and one model call (AC9, AC11).
- **Decision:** one `chat_turn` JSON record per invocation via a child logger `bedrock_agentcore.app.chat` (same inheritance trick as `runtime_app.py`'s curation logger), with `question_chars`, `history_items`, `hits`, `retrieval_ms`, `model_ms`, `outcome` (`ok`, `no_context`, `invalid_request`, `upstream_failure`). It never includes the question, history or answer text (AC6). It is a plain log record, not EMF: chat metrics are not in scope.
- **Decision (Docker):** keep one root `Dockerfile` and select the entrypoint with an environment variable: `CMD ["sh", "-c", "exec python \"${AGENT_ENTRYPOINT:-runtime_app.py}\""]`. The curation agent keeps working with no setting. The chat agent is configured with `agentcore configure -n ai_radar_chat -e chat_app.py ...` and deployed with `agentcore deploy -a ai_radar_chat --env AGENT_ENTRYPOINT=chat_app.py`. Each agent still gets its own ECR repository, its own image tag and its own Runtime, so they are separate images in every operational sense. **This narrows the intent's "separate Dockerfile" to "shared Dockerfile, separate image per agent"**, forced by the toolkit constraint above, and the human reviews it at this gate. Rejected: a second source tree or generated build directory (the build context must contain `src/`), and a `chat_app.py`/`runtime_app.py` dispatcher file (merges two composition roots).
- **Decision (IAM):** `ChatRuntime` (`infra/lib/chat_runtime.py`) mirrors `AgentRuntime`'s trust policy and statement style, with these statements only: `InvokeSonnetCrossRegion` (`bedrock:InvokeModel` on the `us.anthropic.claude-sonnet-4-6` profile ARN in the pinned account plus `anthropic.claude-sonnet-4-6` foundation-model ARNs in us-east-1, us-east-2, us-west-2), `InvokeTitanEmbed` (Titan v2 foundation-model ARN), `CardIndexQuery` (`dynamodb:Query` on `.../table/ai-radar-cards/index/feed-by-score` only), `AgentCoreLogsWrite`, `AgentCoreLogsDescribe`, `EcrImagePull`, `EcrAuthToken`. No secret grant (chat needs none). The pinned account and region follow `agent_runtime.py`'s convention (change both plus tests when moving accounts). The stack is `AiRadarChatRuntime`, output `ExecutionRoleArn`. Rejected: adding statements to the curation role (widens a write-capable role for a read path, forbidden by AC7) and sharing statement code between the two constructs now (only two consumers; the test pins each role's exact statements, which catches drift).
- **Decision (model default):** change `SONNET_MODEL_ID`'s default and its comment, then update the tests that pin the old string. Nothing else about the model call changes. If the live smoke call rejects the `cachePoint`, drop that one element behind the config default and record it as an audit finding, not a silent edit.
- **Decision (live steps):** the executor writes the README runbook for AC10 and the live-check commands (a small `run_chat_agent_smoke.py` is optional and only invokes, never writes). It does **not** run any step that deploys or writes to AWS. The conductor presents each step to the human, runs it only on their word, and records the evidence in `tasks.md` (command, output, timestamp, with account and table printed first, as the backfill does).
