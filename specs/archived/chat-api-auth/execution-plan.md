## Proposed approach
Revisable by the executor if it records why.
- Decision: pass `authorizer=HttpIamAuthorizer()` to the existing `add_routes` call, and drop `cors_preflight` from the `HttpApi` — rationale: a one-route change that keeps the same constructs and logical ids, so CloudFormation updates in place; rejected: `default_authorizer` on the `HttpApi` (it has the same effect with one route, but it is less explicit about which route is authenticated), and a Lambda authorizer or a handler-side check (both spend the Lambda concurrency that AC2 must protect).
- Decision: create the caller with `iam.User(self, "ChatApiCaller", user_name="ai-radar-chat-api-caller")` and one `add_to_policy(PolicyStatement(sid=..., actions=["execute-api:Invoke"], resources=[self.http_api.arn_for_execute_api("POST", "/v1/chat", "*")]))`, exposed as `.caller_user` — rationale: `iam.User` has no `inline_policies` parameter, and `add_to_policy` yields one `AWS::IAM::Policy` attached through `Users`, which is an inline policy in IAM terms; the stage wildcard covers `$default` without hard-coding the stage name; rejected: `HttpRoute.grant_invoke` (it hides the exact ARN that the AC pins), a managed policy (forbidden by AC4), and `iam.CfnUser` with `Policies` (an escape hatch nobody needs here).
- Decision: in the synth tests, scope the Lambda-role statement helper to the policies whose `Roles` reference the Lambda role, and add a separate helper for the policies whose `Users` reference the caller — rationale: the existing `_statements` helper collects every `AWS::IAM::Policy`, so the new user policy would break the "exactly two role statements" test even though the role did not change.
- Decision: `run_chat_api_smoke.py` reads the base URL from `CHAT_API_URL`, takes the question as an optional argument, builds credentials from the default botocore chain (so `AWS_PROFILE=<name>` or `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` both work), prints the caller's account and ARN from `sts get-caller-identity` first, then sends one signed `POST /v1/chat` with `urllib.request` and prints the status and body. Its signing and header building live in one pure function, which takes the URL, body and a `botocore.credentials.Credentials` and returns the headers, so it can be unit-tested offline. Two optional flags for the AC7 negative probes are suggested: `--unsigned` (send without signing) and `--tamper` (change the body after signing, which gives a bad signature). The expired-signature probe can replay a request signed more than 5 minutes earlier, or use a clock offset passed to the pure function — rationale: one script covers every live AC7 probe without curl SigV4 flags; rejected: `curl --aws-sigv4` (curl's SigV4 support and credential handling vary by build, and it puts the secret key on the command line), and the `requests` or `requests-aws4auth` packages (new dependencies).
- Decision: the script prints neither the secret key nor the session token, and it does not print the `Authorization` header — rationale: the key is the only guard.
- Decision: the README runbook replaces the CORS preflight step with the auth steps. It shows the deploy without `-c chat_api_allowed_origins`, a `cdk diff` reviewed before the deploy, `aws iam create-access-key --user-name ai-radar-chat-api-caller` run by the human, with the output piped straight into the frontend server environment and never saved in the repo, and a rotation procedure: create a second key, switch the frontend env, verify a signed 200, `aws iam update-access-key --status Inactive` on the old key, verify again, then `aws iam delete-access-key`. A user can hold at most two keys. It also covers the 403 and signed-200 checks and the Lambda `Invocations` delta check.
